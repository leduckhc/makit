# SPEC-46 — Implementation plan (P0 + P1)

Spec: [`2026-08-07-SPEC-46-cli-as-client.md`](./2026-08-07-SPEC-46-cli-as-client.md) (rev 3)

Ground rules (AGENTS.md): **failing test first**, SOLID/YAGNI, surgical diffs, match existing style.
Commands are the repo-supported ones from [`docs/DEVELOPMENT.md`](../DEVELOPMENT.md): `pnpm test` /
`pnpm typecheck` in `server/`, `flutter test --no-pub` / `flutter analyze --fatal-infos --no-pub` in
`app/`. Two caveats that cost real time: never `pnpm exec tsx --test` (it prunes devDependencies and
hangs — use `pnpm test`, or `node --import tsx --test <file>` for one file), and where `flutter` is
not on `PATH` use the absolute binary.

D1–D17 in the spec are **locked**, and rev 3 closed the last decision gate (the pi-env spike). There
is no decision gate left in this plan. The four contracts below are *implementation contracts the
spec deliberately left to the plan* — they extend locked decisions, none contradicts one.

## Contracts pinned by this plan

### C1 · The capability map (extends D17)

Default-deny, three caps, and **completeness is a test, not a discipline**.

| cap | Who holds it | May dispatch |
| --- | --- | --- |
| *(absent)* | every already-paired phone/app | everything (D17: absent means full) |
| `client` | `cli@<hostname>` (D2) | everything except nothing — same surface as a phone, but *revocable separately*; it is a subject, not a restriction |
| `read` | agent-scoped token (D3) | `sub`, `unsub`, `session.transcript`, `sessions.snapshot` (push-only, no command) |
| `send` | agent-scoped token | `send.message`, `session.action` |
| `spawn` | agent-scoped token | `session.spawn`, `worktree.create` |

Everything not listed for a cap is refused with `WireErrorCode.Unauthorized`. Notably **refused for
an agent token**: `session.kill`, `session.archive`, `session.setAgent`, `ports.*`, `pr.*`,
`worktree.wrapUp`, `worktree.discard`, `devices.*`, and `srv.response` (D13c states the last one).

`CommandRouter` gets one method — `kinds(): string[]` — purely so T4's test can assert every
registered kind appears in the map. Without it the map's failure mode is silent omission, which is
the same class of bug as the `srv.response` hole the rev-2 review found.

### C2 · Where the per-session token lives (extends D3)

**Not** in `devices.json`. Agent tokens live in an in-memory `SessionTokenStore` keyed by sessionId,
minted in `startOpts()` and dropped in the same step that rebuilds it on re-attach.

Rationale, and why the obvious alternative is wrong: `DeviceRegistry` persists to
`~/.makit/devices.json` on every mutation (`registry.ts:172`), so a session token written there
would **survive a crash as a valid credential for a session that no longer exists** — and would show
up in `makit devices`, which D2 exists to make truthful. In-memory also makes the D3 criterion
("rejected once its session ends") true by construction: a restart has no session, so it has no
token. `AuthGate` consults the registry first, then the session store; a session-store hit yields a
principal with `sessionId` set, which is what D9's lineage derivation and D17's fanout gate key off.

Rev 3 constraint this must respect: an env-delivered token **cannot** be rotated without an adapter
restart. So the store is written only from `startOpts()`, never from a timer or a refresh path.

### C3 · `session.transcript` (extends D5)

`cmd {kind: "session.transcript", sessionId, limit}` → `ack {events: SessionEvent[]}`: the **last**
`limit` events, oldest-first, served from `EventStore.read(sessionId)` (which already takes a
`fromSeq`, `event_store.ts:64`) and clamped `1 ≤ limit ≤ 200`. Events are returned **verbatim** —
same wire shape as fanout, no CLI-side projection (D7). Rendering the slice into a fenced block is
CLI work (T13), not server work.

### C4 · Exit `3` vs `4` (extends D8)

The CLI **probes the control socket before opening WSS**, reusing `requireDaemon()`
(`cli/require-daemon.ts`) exactly as today's thin clients do. That yields SPEC-02's message and exit
`3` for free, and it is also where `cli.grant` is called — so the credential and the liveness check
are one round trip. A WSS connection that is then refused, or a `hello` that fails, is exit `4`.

Consequence for P3 (recorded, not built): a **remote** context has no control socket, so `makit ctx`
will need its own down-vs-unauthorized discrimination. No P0/P1 verb is affected.

## Order — P0 fully before P1

P0 is the transport, the credential and the enforcement point; every P1 verb is a client of it.
Within P1, lineage data lands before the verbs that read it, and D13/D14 (the security-sensitive
`reverse_rpc` change plus app work) lands **last**, against a system whose other parts already work.

```
P0  T1 cli.grant + caps on PairedDevice ─▶ T2 principal on AuthGate/WsClient
       ─▶ T3 SessionTokenStore (C2) ─▶ T4 router capability map + completeness test (C1)
       ─▶ T5 fanout gating (D17 rev 3) ─▶ T6 cli/client.ts (WSS client module)
       ─▶ T7 ls + output contract (D7) + exit codes (D8/C4) ─▶ T8 attach re-homed, devices.json gone
────────────────────────────────────────────────────────────────────────────────────────
P1  T9 lineage: protocol + SQLite migration + Flutter DTO ─▶ T10 session.spawn parentId from credential (D9)
       ─▶ T11 depth/fan-out guard ─▶ T12 new (+worktree, D15) ─▶ T13 session.transcript (C3)
       ─▶ T14 send/tail/resume/rm ─▶ T15 stub: awaiting-* + terminal error ─▶ T16 wait (edge-triggered)
       ─▶ T17 run ─▶ T18 manifest render (golden) ─▶ T19 handoff (inherits parent tree)
       ─▶ T20 D13 audience ladder + pending eligibility + response auth ─▶ T21 D14 captions (app)
```

Each task states its **red test** and its **verify** command. A task is not done until its verify
passes and the whole suite still does.

Most of the `ws/` test files named below **do not exist yet** — only
`daemon/control-server.test.ts`, `storage/sqlite_event_store.test.ts` and `adapters/stub.test.ts` do.
The rest (`ws/auth_gate.test.ts`, `ws/command_router.test.ts`, `ws/subscription_hub.test.ts`,
`ws/reverse_rpc.test.ts`, `ws/commands/session.test.ts`, everything under `cli/`) are new files this
plan creates, which is expected: `src/ws/` currently has exactly one test (`throttle.test.ts`), so
P0 is also the task that puts the WS layer under test at all.

## Landed

T1–T21 are all on `feat/cli-client`. Two gaps this plan created and then closed after the fact, both
found by driving the verbs rather than by a failing unit test:

- **`send --attach`** shipped refusing the flag (the upload was judged out of budget). It now uploads to
  `POST /media` with the CLI's own bearer and references the returned `mediaId`, because a text-only
  turn about an image the agent never received is worse than no turn at all. Note the property it
  inherits from the server: the mime is **declared, never sniffed**, so a text file renamed `.png` is
  stored — the same behaviour the app has.
- **`MAKIT_SPAWN_DEPTH` was hardcoded `"0"`**, and `MAKIT_PROJECT_ID` was empty on the launch path
  every app and CLI session actually takes (draft promotion passed no lineage to `startOpts`, while the
  two rarer paths did). `startOpts` now reads lineage from the session itself, so all three call sites
  agree by construction and the depth an agent reads is real. D9's guard never trusted the variable —
  which is exactly why handing out a wrong one was safe to ship and pointless to keep.

## P2 — the terminal as a full peer

Two things were established by reading the code before planning, and they change the shape of this
phase:

- **`makit log` is dropped.** The grammar lists it as "the event log", which is *exactly* what
  `makit tail <id>` without `-f` already prints (the `sub` replay, ending at the ack). A second verb
  for one behaviour is the kind of duplication SPEC-19 spent a spec deleting; `tail --since` already
  covers "from a cursor". If paging over a very long log is ever wanted, that is a `--limit` on `tail`
  answered by `session.transcript`, not a new verb.
- **`approve`/`answer` need no change to D13.** The worry was that a CLI which was not connected when
  a prompt was raised could never answer it, because T20 stores the audience on the pending request.
  It can: `isEligible` stores **session ids** and tests `client.subscribed.has(sid)` at *delivery*
  time, and `sub` already calls `replayPendingTo` (`server.ts:701`). So `makit approve <id>`
  subscribes, receives the replay, and answers — while D13(b)'s lock still holds, because a client
  subscribed to an unrelated session matches nothing in that set.

### U1 · `makit tree` — lineage as a projection (D10)
- **Red:** a `parentId` chain renders as an indented tree with the handoff reason and origin; a forged
  **cycle** in the snapshot terminates rendering (hostile persisted data reaches the client too);
  orphans (a `parentId` naming a session that is gone) render at the root rather than vanishing.
- **Do:** a pure renderer beside `render.ts`; no new wire — `sessions.snapshot` already carries the
  fields. `--json` stays the wire array (D7).

### U2 · `makit ask <id> MSG --wait`
- **Red:** exits `0` printing only the agent's final message; a blocked turn still exits `10`/`11` so a
  script cannot mistake "needs you" for an answer; `--wait` is implied (the verb exists for it).
- **Do:** compose `send.message` + `awaitOutcome` (T16's watcher) + the last `agent.message`.

### U3 · `makit approve <id> [--deny]` · `makit answer <id> TEXT`
- **Red:** subscribing replays a pending `confirmAction` and `--deny` answers `approved: false`;
  `answer` fills an `input`; a prompt for a session the CLI is **not** subscribed to is never
  answered (D13b regression lock, from the client side this time); with no pending prompt the verb
  exits non-zero instead of hanging.
- **Do:** a thin `srv.response` sender on the shared client. **No new authorization path** — the
  server-side check T20 landed is the only one.

### U4 · `session.fork` — SPEC-29's pending item
- **Blocked on a decision, not on code.** `AgentAdapter` has the `fork` *capability* (`adapter.ts:115`,
  codex `true`, pi via ACP `has(sc.fork)`) but **no `forkSession()` method exists anywhere** — the
  seam SPEC-29 named was never cut. So this task must also answer: does a forked thread become a
  session sharing the parent's worktree (like `handoff`, D15 inverse) or take its own tree, and what
  is its lineage `origin`? Fidelity is the whole reason `fork` is not `handoff` (D6), so it cannot
  quietly become a second handoff.

### U5 · "handed off from …" in the app (D10)
- **Red:** a session with `parentId` + `handoffReason` shows the caption; one without shows nothing;
  a `parentId` naming a session the app does not have still renders (the parent may be archived).

## Not in this plan

P2 (`session.fork`, `approve`/`answer`, `ask --wait`, `log`/`tree`) and P3 (contexts/login,
`makit qr --session`) get their own plan once P1 ships — per D12, they compose on this verb set and
should not be designed against imagined ones. Open questions 1–3 in the spec (a parent-side
`session.meta` note, where the manifest lives on disk, the `sessions` alias lifetime) do not block any
task above; Q2 becomes urgent only when an agent-facing skill documents the handoff flow.
