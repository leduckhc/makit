# SPEC-tab-groups — Tab groups: worktree groups + boards

**Status:** Proposed · **Priority:** P2 · **Surface:** desktop chat (`app/lib/desktop/chat/`), desktop settings
**Depends on:** SPEC-desktop-workspace-tabs (workspace: recursive splits + tabs — the tree this spec keys), SPEC-new-session-config-at-spawn (new-session dialog), SPEC-session-lifecycle-resume-list-delete (archive/resume semantics — what a pane ✕ does)
**Supersedes:** SPEC-desktop-workspace-tabs decision 3 ("exactly one layout") and decision 6's "no worktree/workspace switch". SPEC-worktree-scoped-panes stays superseded, but this spec restores its keyed-layout *mechanism* under a different owner — see "Relationship to SPEC-worktree-scoped-panes and SPEC-desktop-workspace-tabs".
**Server changes:** none. Groups are a pure client-side view over `sessions.snapshot`.

---

## Problem

Two legitimate needs pull the layout in opposite directions, and every previous
spec picked one and lost the other:

1. **Structure.** "Show me *this* worktree — every agent working on this branch,
   and nothing else." SPEC-worktree-scoped-panes delivered this by making the worktree own the
   layout, which made need 2 impossible.
2. **Multitasking.** "Show me *these* agents — the four I care about right now,
   across branches and repos." SPEC-desktop-workspace-tabs delivered this with one free-form,
   worktree-agnostic layout, which made need 1 impossible: selecting a worktree
   deliberately does *not* swap the canvas, so a branch's agents can only be
   gathered by hand, and nothing stops a foreign session sitting among them.

The needs are not actually in conflict. They differ in exactly one respect:
**who decides what is on the canvas.** Need 1 wants membership *derived* from a
worktree; need 2 wants it *curated* by the user. Neither spec made membership an
explicit, nameable thing, so each had to hard-code one answer.

Secondary problems this fixes:

- Splitting a pane (`⌘D`) seeds a tab with **no** worktree hint
  (`workspace_controller.dart:133`), so ⌘D from a session on `feat/x` offers a
  fresh branch, while the `+` in the same tab strip prefills `feat/x`
  (`split_view.dart:358`). Inconsistent for no reason.
- `/new` (`client_commands.dart:66`) spawns with no worktree at all. Since
  SPEC-new-session-config-at-spawn's follow-up work made the client responsible for resolving the
  worktree before spawning, this now silently runs an agent in the repo's
  primary checkout.

## Goal

Make **membership** a first-class object: a **group**. One canvas, one sidebar,
two kinds of group.

- **Worktree group** — membership derived: every session on branch X, nothing
  else. New sessions on that branch join automatically. Free to close and
  reopen, because it can always be rebuilt from the live session list.
- **Board** — membership curated: a hand-picked list that may span branches and
  repos. Nothing joins unless you add it.

Both render through the **existing** SPEC-desktop-workspace-tabs split/tab tree. The rendering,
splitting, tab strips, drag payloads, and reveal logic are unchanged; what
changes is that there are now *many* trees, keyed by group, and one of them is
active.

**Mobile is unchanged.** Groups are a desktop-window concept; mobile keeps its
repo → worktree list and its new-session sheet.

## Vocabulary (frozen naming)

| Term | Definition |
|---|---|
| **Group** | a **view** — a named set of sessions plus its own split/tab tree. Never a place; a group cannot tell an agent where to run. |
| **Worktree group** | `kind: worktree`. Membership **derived** from `(projectId, worktreePath)`. |
| **Board** | `kind: board`. Membership **curated**: an explicit ordered list of session ids. |
| **Membership** | the set of sessions a group shows. Derived or curated — never both. |
| **Active group** | the one group whose tree is on the canvas. |
| **Scope** | a worktree group's `(projectId, worktreePath)` pair. |
| **Workspace** | *retired as a singular noun.* SPEC-desktop-workspace-tabs's single workspace becomes the **active group's tree**. |

> The sidebar is the world; a group is a window onto part of it. Every decision
> below follows from that sentence.

## Decisions (frozen)

1. **Two kinds of group, distinguished only by membership.** Worktree groups are
   derived; boards are curated. There is no third kind and no group that is
   partly both.

2. **Each group owns its own split/tab tree**, persisted independently. Switching
   groups swaps the tree on the canvas and nothing else — the sidebar never
   redraws.

3. **A session may appear in many groups, but at most once per group.** Adding a
   session already in the active group focuses its existing tab (SPEC-desktop-workspace-tabs
   decision 5, now scoped per group rather than globally).

4. **Worktree-group membership is enforced, and an explicit add is what
   converts.** An **explicit add gesture** — drag-and-drop, the sidebar hover
   `+`, or ticking a session in the agent picker — that targets a worktree group
   with an out-of-scope session is never refused; instead the group is
   **converted to a board** containing its current members plus the newcomer,
   the new board becomes active, and the original worktree group is left
   untouched. Auto-name: `<branch> +1`.

   > Conversion is reachable **only** from those three gestures. Merely *looking
   > at* a session never converts anything — see decision 15.

5. **A new session started elsewhere never steals the canvas.** A session
   appearing in `sessions.snapshot` (started from the phone, another desktop,
   the CLI) joins its worktree group's membership silently. Its group is only
   opened if the user clicks it. The active group is never switched implicitly —
   except by decision 4 (an explicit add) and decision 15 (an explicit
   navigation), both of which are direct, unambiguous user actions.

6. **A board silently unpins members that vanish.** When a session is archived,
   killed, or otherwise absent from `sessions.snapshot`, it is removed from every
   board's member list (and its tab closed). No dead tiles, no restore
   affordance. This extends the existing prune
   (`desktop_session_prune.dart`) rather than adding a second mechanism.

7. **Three distinct closes, never conflated.**
   - ✕ on a **worktree group tab** → closes the view only. Sessions keep
     running, the worktree is untouched, and clicking the branch in the sidebar
     rebuilds an identical group. Nothing is stored to make this possible.
   - ✕ on a **board tab** → the board moves to **recently closed boards** (a
     persisted, capped list) and a toast offers immediate Undo. Its sessions keep
     running.
   - ✕ on a **pane/tab** → on a worktree group, archives that session (SPEC-session-lifecycle-resume-list-delete,
     unchanged); on a board, **unpins** it and the agent keeps running.
     **Unpin-vs-archive is a property of the active group's kind, not of the
     affordance:** it is decided inside `closeTabAndArchive`, so the tab ✕, the
     `⌘⇧W` shortcut (`closeActiveTab`), and any future entry point all inherit
     the same behaviour. No call site may special-case it.
   - **Delete worktree** (sidebar menu) → unchanged: removes the git worktree and
     archives its sessions; its worktree group disappears with its scope. If that
     group was **active**, focus moves to the neighbouring group tab, mirroring
     `_focusAfterRemoval`'s existing behaviour for splits.

8. **Recently closed boards persist** (default cap: 10, most-recent-first).
   Reopening restores the member list, the layout, and the group's slot in the
   tab order, and removes it from the list. **Membership is filtered against the
   current `sessions.snapshot` on reopen** — a board closed for a week may point
   at sessions since archived, and decision 6's live unpin cannot reach a closed
   board. A board left with **no surviving members** still reopens, empty, with
   the agent picker already open (it is a named thing the user made; it is not
   silently discarded).

9. **The threshold is a placement policy, not a layout engine.** A group's tree
   is the user's (decision 2) and is **never rearranged automatically**. The
   preference `layout.autoSplitThreshold` (default **3**) decides only **where a
   newly shown session lands**:
   - members currently shown < *N* → open it as a **new split** beside the others;
   - members ≥ *N* → open it as a **new tab** in the focused split.

   Any manual arrangement — splitting, closing a split, dragging a tab between
   strips — implicitly sets the group's `layoutOverride` to whatever the user
   just built, and from then on placement follows that override rather than the
   threshold. The `Split | Tabs` toggle in the membership bar sets the override
   explicitly and re-lays-out the group **once**, on that click only.

   > Changing the preference never re-lays-out an existing group; it only
   > affects where the *next* session lands in groups with no override.

10. **The title strip hosts group tabs (left) and the IDE launcher (right).**
    The strip's branch label (`_WorktreeTitle`) is removed — the active group tab
    carries the branch for worktree groups, and per-pane origin chips carry it on
    boards. The strip itself therefore names no branch when a board is active,
    which is deliberate: the origin chip sits on the pane you are actually
    reading, closer to the eye than the window strip.

11. **The IDE launcher keeps its current appearance and targets the active pane.**
    `OpenInIdeButton` is **visually unchanged**: the same 24px bordered split
    button, `[preferred-editor logo | ▾]`, icon-only — it gains **no** text label.
    `▾` chooses the **app** (the existing `IdeTarget` enum, persisted via
    `preferredIdePreference`) and nothing else; it never offers "some other
    worktree".
    - What it opens is named in the **menu header** (`Opens the active pane ·
      ~/.worktrees/…`), not on the button, so the control cannot lie while staying
      icon-sized.
    - On a board the target follows pane focus.
    - With **no pane focused** (an empty worktree group — decision 20) it targets
      the group's own scope, since a worktree group always owns a folder. Only a
      board, which owns none, can have nothing to open; there the button is
      disabled.

12. **The group tab strip scrolls horizontally** when it overflows. No overflow
    menu, no collapsing, no wrapping to a second row.

13. **`+` means "start an agent here" in a worktree group and "add to my view" on
    a board.** In a worktree group the scope answers *where does it run?*, so `+`
    shows the in-pane starter (harness cards + config pills + composer, already
    implemented as `WorktreeStarter`). On a board there is no scope, so `+` opens
    the **agent picker**; its `New session…` row opens the SPEC-new-session-config-at-spawn dialog and
    pins the result to the board.

14. **Four ways to add an existing session to a board**, all equivalent: the
    trailing `+ Add agent` region, the `+` in the tab strip, a hover `+` on the
    sidebar session row, and drag-and-drop from the sidebar (already wired via
    `Draggable<SessionDragData>`).

15. **Sidebar clicks navigate; they never mutate membership.**
    - A **worktree row** activates that worktree's group, minting it if it does
      not exist. This *replaces* SPEC-desktop-workspace-tabs decision 6's "no worktree switch" for
      worktree rows. **Disclosure is a separate caret**: the row navigates, the
      caret expands/collapses. One tap doing both meant peeking at a branch's
      children yanked the canvas, and moving the canvas collapsed the row you
      were reading. Rows with nothing to disclose have no caret but reserve its
      width, so branch names stay aligned.
    - A **session row** activates a group that **already contains** that session,
      then reveals its tab there, resolved in this order: (a) the active group, if
      the session is already a member — no group switch, exactly SPEC-desktop-workspace-tabs
      decision 6; (b) its own worktree group, if open; (c) any open board holding
      it (most recently activated wins); (d) otherwise mint its worktree group
      and activate that.

    A session click therefore **never injects a session into the group you are
    looking at**, and so can never trigger decision 4's conversion. Reading a
    `main` agent while scoped to `feat/login` takes you to `main`'s group; it does
    not turn `feat/login` into a board.

16. **`⌘1`…`⌘9` switch to the 1st–9th group.** Groups past the ninth have **no
    shortcut** — they are reached by clicking or by scrolling the strip
    (decision 12). No wrap-around, no "⌘9 = last". All existing bindings
    unchanged.

17. **Splitting inherits the source tab's worktree.** `⌘D`/`⌘⇧D` seed the new
    tab with the active tab's worktree, so it lands on the in-pane starter rather
    than the no-worktree placeholder. This makes ⌘D and the tab-strip `+` agree.

18. **`/new` starts an agent in the current pane's worktree and joins the active
    group.** No dialog. On a board it is also pinned. This replaces today's
    worktree-less spawn.

19. **Fresh launch → one worktree group** for the most recently active session's
    worktree, or an empty board named `Board 1` when there are no sessions.

20. **An empty worktree group goes straight to the starter.** A group whose scope
    currently has no sessions (e.g. the user clicked a branch nobody is working
    on) renders `WorktreeStarter` for that scope — the branch already answers
    *where does it run?*, so there is nothing to ask and no placeholder step.
    `EmptyPaneStarter` (the "New session" button that opens the SPEC-new-session-config-at-spawn dialog)
    is reached only when there is no worktree at all: an empty tab on a board.

21. **Boards may contain empty tabs.** Membership counts **sessions**; a tab with
    `sessionId == null` is part of a board's *tree*, not its *membership*. Such a
    tab renders `WorktreeStarter` when it carries a worktree hint (SPEC-desktop-workspace-tabs
    decision 4) and `EmptyPaneStarter` otherwise. Migration therefore preserves
    the user's existing empty tabs verbatim (see Plan step 3).

22. **Mobile unchanged.**

## Relationship to SPEC-worktree-scoped-panes and SPEC-desktop-workspace-tabs

This is the third pass at the same decision, so the difference must be explicit
or it reads as a flip-flop.

| | SPEC-worktree-scoped-panes | SPEC-desktop-workspace-tabs | **SPEC-tab-groups** |
|---|---|---|---|
| Layouts | one per worktree (`Map<path, tree>`) | exactly one, shared | one per **group** (`Map<groupId, tree>`) |
| Cross-worktree view | impossible | the only mode | the **board** kind |
| Worktree-scoped view | the only mode | impossible by design | the **worktree group** kind |
| Who owns membership | the worktree, implicitly | the user, implicitly | **the group, explicitly and visibly** |

SPEC-worktree-scoped-panes and SPEC-desktop-workspace-tabs each hard-coded one answer to a question they never asked out
loud. SPEC-tab-groups asks it: *who decides what's on the canvas?* — and lets both
answers coexist because they are now labelled, switchable objects with a
conversion rule between them (decision 4).

Mechanically this **restores SPEC-worktree-scoped-panes's keyed-map persistence**, which SPEC-desktop-workspace-tabs
removed. The key is a group id rather than a worktree path, and swapping is
driven by an explicit group switch rather than as a side effect of selecting a
session. SPEC-worktree-scoped-panes remains superseded as a *model*; its keying is rehabilitated as
an implementation detail.

## Target model

### Group (new — `app/lib/desktop/chat/groups/group.dart`)

```dart
enum GroupKind { worktree, board }

/// How a group places a newly shown session (decision 9). Not a rendering mode:
/// the tree itself is always whatever the user last arranged.
enum LayoutMode { split, tabs }

@immutable
class Group {
  final String id;
  final GroupKind kind;
  final String label;            // branch name, or the board's name
  final String? projectId;       // worktree groups only
  final String? worktreePath;    // worktree groups only  (the scope)
  final List<String> members;    // boards only (ordered, no duplicates)
  final LayoutMode? layoutOverride; // null → follow the threshold
  final WorkspaceState tree;     // this group's SPEC-desktop-workspace-tabs split/tab tree
}
```

- `toJson`/`fromJson` mirroring `split_node.dart`'s tagged style; a corrupt group
  is dropped, not fatal.
- Membership is resolved, never stored, for worktree groups:
  `sessions.where(s => s.projectId == projectId && s.worktreePath == worktreePath)`
  — ordered by the sidebar's existing `sortWorktreesForDisplay`-adjacent rules
  (creation order is fine).

### GroupsController (new — `groups/groups_controller.dart`)

Follows `WorkspaceController`'s exact pattern (nullable prefs → ephemeral,
`.load(prefs)`, write-through full dump), under a new key
`kGroupsPrefsKey = 'desktop.groups'`:

```text
state: { groups: List<Group>, activeGroupId: String, recentlyClosed: List<Group> }
```

- `activate(id)`, `openWorktreeGroup(projectId, path, label)` (mint-or-activate),
  `revealSession(sessionId)` (decision 15's a→d resolution), `newBoard()`,
  `closeGroup(id)` (worktree → drop; board → push to `recentlyClosed`, capped at
  10), `reopenBoard(id)` (filters members against the live snapshot),
  `undoClose()`, `addMember(groupId, sessionId)` (**converts** per decision 4 when
  the group is a worktree group and the session is out of scope), `removeMember`,
  `setLayoutOverride`, `reorderGroups`, and `commitTree(groupId, WorkspaceState)`.

### How the existing `WorkspaceController` is reused (the load-bearing bet)

The goal is that **every tree mutation** — `divideActive`, `openTab`,
`revealSession`, `closeActiveSplit`, `setRatio`, `unbindSession`, tab reorder —
keeps its current implementation and its current tests. That requires one honest
change, not zero:

- Today `WorkspaceController._commit` calls `_persist`, which writes the whole
  tree to `SharedPreferences` under `kWorkspacePrefsKey`
  (`workspace_controller.dart`, `_commit`/`_persist`). With many trees, the
  controller can no longer decide what gets written.
- **Change:** the controller is constructed with an injected commit sink instead
  of `SharedPreferences`:

  ```dart
  WorkspaceController(this._onCommit, WorkspaceState initial);
  WorkspaceController.ephemeral();            // _onCommit = null (tests)
  // _commit(next) { state = next; _onCommit?.call(next); }
  ```

  `GroupsController` supplies the sink (`(tree) => commitTree(activeId, tree)`)
  and owns the single write to `kGroupsPrefsKey`. `desktop_app.dart` builds the
  groups controller and derives the workspace controller from it, replacing
  today's `WorkspaceController.load(prefs)` + `overrideWith` pair.
- **Test impact, stated honestly:** the ~4 tests in
  `test/desktop/chat/workspace_controller_test.dart` that assert
  `kWorkspacePrefsKey` directly (persist-on-mutate, corrupt-JSON restore,
  bogus-node restore, restore-from-blob) **move** to the groups layer and are
  rewritten against `kGroupsPrefsKey`. The remaining ~39 tree-mutation tests are
  untouched — that is the actual value of this design, and it is worth stating as
  a number rather than as "unchanged".
- **Non-goal:** folding group state into `WorkspaceController`. It would put
  membership, conversion, and recently-closed logic into the class every layout
  test depends on. Keep the two controllers separate even if the indirection
  feels like ceremony.

## Risks & notes

- **Persistence migration is the one-way door.** Step 3 rewrites the shape of a
  key users already have. The migration must be lossless (old tree → one board)
  and defensive: any decode failure falls back to decision 19's fresh-launch
  state rather than throwing.
- **The commit-sink refactor is the whole bet.** `WorkspaceController` keeps
  every tree mutation and ~39 of its tests; only its persistence moves. If the
  indirection feels like ceremony, the temptation will be to fold group state
  into the controller — which would rewrite all of those tests and put
  membership/conversion logic in the class the whole layout depends on. Resist.
- **Conversion is a surprising state change** (decision 4), which is why it is
  reachable only from three explicit gestures and never from navigation
  (decision 15). It must be announced (toast, as mocked) and the auto-name is
  deliberately ugly (`feat/login +1`) so the user renames it. Accepted for v1.
- **Worktree groups are free but not free to *compute*.** Membership is derived
  on every snapshot; with many groups this is a per-snapshot O(sessions ×
  groups) pass. Trivial at realistic scale, but keep it out of build methods.
- **`⌘1…⌘9` may collide** with anything the OS or a future in-pane widget wants;
  the keymap already has conflict detection (`Keymap.conflictFor`), so bind
  through it rather than hard-coding.
- **Board ordering** is insertion order for v1. No manual reordering of members
  (tabs can already be dragged within a split, which is enough).

## Out of scope

- Renaming groups inline (boards get auto-names; a rename affordance can follow).
- Nested / grouped groups, colour-coding beyond the two kind swatches, per-group
  icons.
- Sharing or syncing groups across devices (purely local prefs).
- Mobile groups.
- Server-side awareness of groups (there is none, by design).
- Multi-window (each window owning its own active group).
