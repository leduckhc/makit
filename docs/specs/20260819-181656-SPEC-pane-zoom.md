# SPEC-pane-zoom — Zoom one pane, not the whole app

**Status:** drafted · **Priority:** P2 · **Surface:** app (desktop)
**Depends on:** SPEC-tab-groups (the split tree, `Split`, and the `⌘1…⌘9` bindings this must not
collide with), SPEC-desktop-settings-rework (the global `appearance.textScale` preference this
composes with)

---

## Goal

A pane on a 4K screen shows text that is too small. The user wants to make one pane bigger, and
keep the rest of the window as it is. Today the only control is **Settings → Appearance → Text**,
a global slider from 0.9 to 1.3. It scales every pane and all chrome together, it needs four clicks,
and it cannot go far enough.

This spec adds **per-pane zoom** to the desktop app:

- `⌘=` zooms in, `⌘-` zooms out, and `⌘0` returns to 100%.
- A trackpad pinch zooms the pane under the pointer.
- `⌘`+wheel (or `⌃`+wheel) zooms, and does not scroll the transcript.
- The native **View** menu lists Zoom In, Zoom Out and Actual Size, with their shortcuts.

Only the active pane changes. The sidebar, the title bar and the tab strip hold still.

## The existing mechanism

`desktop_app.dart:316` wraps the whole app once:

```dart
final textScaler = TextScaler.linear(ref.preference(textScalePreference));
// …
builder: (context, child) => MediaQuery(
  data: MediaQuery.of(context).copyWith(textScaler: textScaler),
  child: child,
),
```

Per-pane zoom **extends** this. It does not add a second global scale.

## Decisions

| | decision | why |
|---|---|---|
| **D1** | Zoom scales text through `MediaQuery.textScaler`. It does not use `Transform.scale`. | The pane reflows to its real width, so a wide code block never clips and no horizontal scrollbar appears. `Transform.scale` instead shrinks the pane's logical width as the user zooms in. That clips the very content the user zoomed in to read. Text stays crisp either way, but only reflow keeps the layout honest. |
| **D2** | The factor lives on `Split`, as `zoom`. It does not live on `Tab`, and not in a side table keyed by split id. | The user zooms a *pane*, so the value belongs to the pane. It then persists with the layout tree for free, and it dies with the pane. A side table keyed by split id leaks an entry for every closed pane. |
| **D3** | The effective scale is `globalTextScale × paneZoom`, clamped to **0.6 – 2.4**. | The global setting keeps its meaning, and a zoomed pane still follows it. The clamp applies to the product, so `1.3 × 2.4` cannot reach 3.1. |
| **D4** | The keyboard steps a fixed 14-stop ladder: 0.6, 0.67, 0.75, 0.8, 0.9, **1.0**, 1.1, 1.25, 1.4, 1.6, 1.8, 2.0, 2.2, 2.4. | Browser-style stops are predictable, and repeated presses land on the same values every time. The ladder is denser near 1.0, where users spend their time. 1.0 is also an exact stop, so `⌘0` is reachable by stepping. |
| **D5** | Pinch and modifier+wheel set a continuous factor inside the clamp. The keyboard steps to the next stop in the direction it travels. | A pinch that snapped to 14 stops feels notchy. A keyboard press that left 1.03 behind would make `⌘=` unpredictable. So `⌘=` from 1.03 lands on 1.1, and `⌘-` lands on 1.0. Each input gets the behaviour it needs. |
| **D6** | Only the pane content scales — the transcript and the composer. The sidebar, title bar, group bar and tab strip keep the global scale. | This is what "per-pane" means. Chrome that moved with the pane would shift the layout under the pointer mid-gesture. The global preference stays the way to scale chrome. |
| **D7** | The native **View** menu gains the three items. We extend `macos/Runner/Base.lproj/MainMenu.xib` and forward each item to Dart on a `MethodChannel`. We do **not** adopt Flutter's `PlatformMenuBar`. | `PlatformMenuBar` replaces the XIB menu bar, and `PlatformProvidedMenuItemType` offers no Cut, Copy, Paste, Undo or Select All. Adopting it would force us to hand-roll the Edit menu in Dart. Those items then no longer reach the focused native text view. That risks the composer's text editing to add three menu items. |
| **D8** | Dart owns the bindings. It pushes each item's label and key equivalent down to Swift when the keymap changes. | `ShortcutAction` is already user-rebindable in Settings → Shortcuts. A key equivalent hard-coded in the XIB would silently ignore a rebind. macOS also consumes a menu key equivalent before Flutter sees the key. One source of truth avoids both faults. |
| **D9** | The reset item is named **Actual Size**, not "Zoom". | `Window ▸ Zoom` already exists in the XIB, and means *maximise the window*. Two menu items named Zoom would teach the wrong thing. |
| **D10** | A pane whose zoom is not 100% shows a small `120%` chip in its tab strip. A click on the chip resets that pane. | Zoom is otherwise invisible state that survives a restart. A user who zooms out far, and forgets, has no way to explain why one pane looks wrong. The chip is also the only affordance that works without a keyboard. |
| **D11** | `⌘0` reuses `digit0`. | Groups already own `⌘1…⌘9` (SPEC-tab-groups). `digit0` is unbound, so `conflictFor` stays quiet. |
| **D12** | The wheel factor is exponential in the scroll distance, and one "notch" is 100 logical pixels. | A fixed factor for each `PointerScrollEvent` is wrong for a trackpad. A trackpad reports one gesture as many small events, so a flick would race to the limit. An exponential factor composes: twenty 5-pixel events equal one 100-pixel event. The zoom then follows how far the user scrolled, not how many events that took. |
| **D13** | A tab edit never changes the pane's zoom. Every rebuild goes through `Split.copyWith`. | Zoom belongs to the pane (D2), so switching, adding, closing or reordering a tab must not reset it. A `Split(...)` literal drops any field it does not name, which caused exactly that bug. `copyWith` closes the class against the next added field too. |
| **D14** | A special key maps to its AppKit function-key character. An unmappable key sends no key equivalent. | AppKit matches a key equivalent against the input one keypress produces. A rebind to `⌘↑` would otherwise send the label `arrow up`, which can never match. A menu item with no shortcut beats one with a shortcut that cannot fire. Flutter still handles the chord. |
| **D15** | The readable content column is **1140 pt** wide. That is 50% more than the old 760 pt. Pane zoom does not change it. | The old column left most of a wide display empty. The chat then filled a narrow strip in a large window. The width stays constant under zoom on purpose. A column that grew with the zoom would move the text under the pointer mid-gesture. It would also reach the pane edge at a high zoom. Zoom keeps its one job from D1: bigger glyphs, same column. |

## Non-goals

- **Zooming chrome per pane.** The sidebar and title bar follow the global preference only (D6).
- **A zoom HUD.** The chip in D10 covers feedback. A floating overlay adds an animation and a timer
  for no extra information.
- **Zoom on the phone.** The phone has one pane and a system text-size control. Nothing here
  crosses the wire, so the protocol and the server do not change.
- **Retiring the global slider.** It still scales chrome, which pane zoom deliberately does not.

## Plan

1. **Model.** Add `zoom` to `Split`, defaulting to 1.0. Omit the key from `toJson` when it is 1.0,
   and default it in `fromJson`, so a persisted layout from an older build still loads.
2. **Ladder.** Add a `PaneZoom` value type that owns the stops, `stepIn`, `stepOut`, the continuous
   `nudge`, and the compound clamp. Keep it free of Flutter, so it unit-tests directly.
3. **Controller.** Add `setZoom` / `stepZoom` / `resetZoom` to `WorkspaceController`, each acting on
   `activeSplitId`.
4. **Actions.** Add `zoomIn`, `zoomOut` and `zoomReset` to `ShortcutAction`, bind them in
   `Keymap.defaults()`, and dispatch them in `DesktopKeymapScope._invoke()`.
5. **Gestures.** In the pane body, add a `Listener` for `onPointerSignal` (modifier+wheel) and
   `onPointerPanZoomUpdate` (trackpad pinch).

   **Pinch is safe.** `Scrollable` reads only the *pan* delta of a pan/zoom sequence, so reading
   `event.scale` in an outer `Listener` does not fight it.

   **The wheel needs a gate.** `Scrollable._receivedPointerSignal` registers with the
   `PointerSignalResolver`, the resolver keeps the **first** registrant, and `GestureBinding`
   dispatches a signal deepest-first. So the transcript's `Scrollable` always wins over an outer
   `Listener`, and a naive implementation zooms *and* scrolls. The fix is to make the transcript
   refuse the offset while a zoom modifier is held: `shouldAcceptUserOffset` returning false makes
   `Scrollable` return before it registers, which lets the pane's `Listener` win. Expose "a zoom
   modifier is held" as a listenable, and swap the transcript's physics to
   `NeverScrollableScrollPhysics` while it is true. Wrap only the list in the rebuild, not the pane.
   Browsers behave the same way: with `⌘` held, the wheel zooms and never scrolls.
6. **Apply.** Wrap the pane content in the combined `TextScaler` from D3.
7. **Chip.** Render the percentage in the tab strip when zoom is not 1.0 (D10).
8. **Menu.** Add the three items to the View menu, and forward a click to Dart. They are built in
   Swift rather than hand-written into the XIB, because Dart pushes the labels and key equivalents
   (D8) and generated items keep one source of truth. `MainMenu.xib` still owns the bar.

## Verification

**Unit** — `PaneZoom`: every ladder step from each stop; `stepIn` at 2.4 and `stepOut` at 0.6 hold
still; `nudge` clamps; the product clamp holds `1.3 × 2.4` at 2.4; stepping from a continuous value
a pinch left behind. `Split`: JSON round-trip with zoom set, legacy JSON with no `zoom` key loads at
1.0, and a corrupt stored value is clamped.

**The wheel gate** — `ZoomAwareScrollPhysics` refuses a user offset while a zoom modifier is held and
accepts one otherwise, and `applyTo` keeps the parent physics. This is the regression that would be
silent, so it is pinned directly instead of through the widget tree.

**The wheel factor** — `wheelZoomFactor` is symmetric, and twenty 5-pixel events equal one 100-pixel
event (D12). That property is what stops a trackpad racing to the limit.

**Zoom survives a tab edit** — `addTab`, `removeTab`, `activateTab` and `reorderTab` all keep the
pane's zoom, and so do `revealSession`, `revealWorktree`, opening a tab and closing the last tab of
the only pane (D13). `copyWith` keeps and clamps the zoom it is not given.

**Special keys** — the arrows, F1 to F12 and the common editing keys map to their AppKit characters.
An unmappable key sends no key equivalent at all (D14).

**The content column** — the pane lays its transcript and its composer out at the same 1140 pt
column. A zoomed pane lays them out at 1140 pt too (D15). A break in the zoom independence gives no
visible signal. The test pins a measured width, not a constant read back.

**Widget** — `⌘=` scales the active pane and leaves its neighbour untouched; `⌘0` restores 100%; each
pane keeps its own scale; the tab strip stays at the global scale; `⌘`+wheel zooms the pane **under
the pointer** and focuses it, while a bare wheel does not zoom; the chip appears off 100%, states the
percentage, and resets the pane it sits in rather than the active one.

**The menu contract** — the `setItems` payload carries the three ids, labels, AppKit key equivalents
and modifier masks; it follows a rebind and lower-cases the key. An unknown or non-zoom id coming
back is ignored instead of thrown on the platform thread.

**Verified on the real macOS app** — `flutter build macos` compiles the Swift and the project change,
and the running app's accessibility tree lists `View ▸ Zoom in / Zoom out / Actual size` above the
XIB's own full-screen item. A bogus menu path is refused, which is what makes that check meaningful.

Not yet confirmed visually: that AppKit draws `⌘=` / `⌘-` / `⌘0` beside the three items. The payload
is unit-tested and AppKit renders a `keyEquivalent` itself, so the risk is low.

**Gates** — `flutter analyze` clean under `--fatal-infos`, and `flutter test` green. `e2e.sh` is not
required: no change crosses the app ↔ server boundary.
