## What implementation changed about the plan

Two things the spec had wrong, both caught by its own tests rather than by review:

1. **D1 was not sufficient.** The four-option shape still overflowed by 4.7 px at 320 pt after the
   layout fix, and codex's model label still showed only 49 % of `gpt-5.6-codex` at 375 pt, because
   its two read-only chips were eating the row. The spec's own deferral trigger — "an agent that
   ships a shape which overflows or ellipsizes a required label" — was therefore already met by
   codex, so ladder step 2 (chips yield) moved from non-goal to **D5** and was built. That closed
   both the 4.7 px overflow and codex's label.
2. **"Not ellipsized at 375 pt" was still too strong for pi.** A 15-character model name wants
   187.5 pt and the row can grant 183 pt even with no chips; the missing 4.5 pt could only come from
   the avatar, `[+]`, send or the ring. So the criterion became: whole at **393 pt** (every current
   iPhone), **≥ 95 %** at 375 pt (SE/mini). Measured, not negotiated.

## Order, and why this order

Reviewed and reordered: an earlier draft had one characterisation test spanning the whole change,
which cannot work. `footerTrailing` does not exist until T2 and the real screens stay miswired
until T5, so a single test would have to be *edited* between red and green — making changed test
input part of the fix. Instead:

- **T1** tests the contract at the `Composer` level and fails because the parameter is absent.
- **T3** is *not* a RED task: its fixtures pass the ring via `footerTrailing`, so it cannot compile
  before T2. It lands after the fix as the regression net over the four shapes and three widths,
  with a vacuity check instead of a red run.
- **T5** tests the **call sites** and fails until the ring actually moves. Without it, `Composer`
  could be correct while `SessionScreen` still starves its pill — the exact bug class this spec is
  about.
- **T4** comes after the layout tasks on purpose: a shorter label makes width assertions easier to
  satisfy, so the layout must already be proven with the **long** name. Otherwise T4 masks a
  mistake in T2.

## T1 — the contract test (RED)

`app/test/composer_test.dart`.

- RED: `Composer(footerTrailing: …)` does not compile → the parameter does not exist.
- Measure with a **test-owned probe**: a `LayoutBuilder` passed as the single `footerActions` entry
  that records the `maxWidth` it is granted. Pump the same composer twice at the same width — once
  with the ring as a second `footerActions` entry (today), once with it as `footerTrailing` — and
  assert the probe is granted ~50% in the first case and `total − 36 − 6` in the second.
- **Do not measure the collective `Expanded` actions region, and do not add a production `Key` for
  it.** Both reviewers caught this in the first draft: that region is full-width either way and
  becomes 42 pt *narrower* when the ring moves out, so the assertion would fail while the fix is
  correct. A granted constraint is also immune to text-metric drift, which a rendered width is not.
- The probe lives in the test file only — no production code exists for testability's sake.

## T2 — `footerTrailing` (GREEN for T1)

`app/lib/ui/composer/composer.dart`.

- Add `final Widget? footerTrailing;` (default `null`), documented as *intrinsically sized*, with
  the reason inline: a `Flexible` sibling reserves its share even when it uses less
  (`FlexFit.loose`), which is what starved the pill.
- `_buildExpanded`: keep `Expanded(child: Row(footerActions…))` unchanged, then the trailing
  control before `_buildPlus()`. No key, no test hook: each action's existing `Padding(right: 6)`
  supplies the gap, and T1 measures a granted constraint via its own probe.
- Verify: T1 green; every existing composer test still green (the default keeps today's behaviour
  for callers that pass nothing).

## T3 — shape × width characterisation (post-change regression coverage)

`app/test/composer_footer_space_test.dart` (new). This file is what makes the spec's evidence table
reproducible: the original numbers came from a throwaway probe, and this pumps the same four shapes
at the same three widths permanently. The pre-fix figures can be reproduced from it by moving the
ring back into `footerActions` in its `pumpFooter` helper.

**Not a RED task.** Its fixtures pass the ring via `footerTrailing`, which does not exist until T2,
so it cannot compile — let alone fail correctly — beforehand. The RED that drives the layout fix is
T1's probe; T3 is the regression net that keeps the four shapes green afterwards. Reviewer round 3
caught the earlier draft claiming otherwise.

- A helper that pumps a `Composer` at a given width with a given `configOptions` list plus the ring
  in the trailing slot, returning `(exception, labelWidths, didEllipsize, naturalWidths)`. Fixtures
  seed a non-null `sessionUsageProvider` with both halves of the ratio, or the ring is 0 pt and
  every assertion about it is vacuous (`context_usage.dart:204-208`).
- Table-driven: the **three shipping shapes** × {320, 375, 700} pt, plus the hypothetical
  four-option shape at the same widths. The four-option case was initially asserted as a **known
  4.7 px overflow at 320 pt**; building D5 (chips yield) closed it, and the assertion was inverted
  to "must not overflow" in the same change that closed it. At 700 pt its pills share the row rather
  than each getting their natural width; the test asserts the row stays legal and that **all four
  controls are still rendered**, but not that any particular label clips — that is font-dependent,
  and a fit/no-fit flip there means nothing to a user.
- Also asserts, after review: the ring at full size for **every** shape (not just shipping ones),
  that both chips disappear together, that unbounded constraints keep them, that accessibility text
  scaling makes them yield sooner, and that nothing in the row is scrollable (D4).
- Scope: acceptance criteria **1, 4 and 5 only**, asserted with the **long, unshortened** label.
  Criterion 3 (no ellipsis, exact shortened text) belongs to T4 and must not appear here — it
  cannot pass before `shortModelLabel` exists, and a test that crosses that boundary would have to
  be edited between red and green.
- **No pt floors on labels** — compare against an unconstrained-parent baseline for "natural
  width". Exact pt values are font-metric-dependent; a floor would turn a text-rendering change
  into a failing layout test.
- Vacuity check performed **by hand** (it cannot be automated — the old wiring no longer exists in
  the code): with the ring moved back into `footerActions`, shape 4 throws
  (`overflowed by 18 pixels`) and the labels ellipsize. The same check at both call sites produced
  the sharpest numbers in the change: the label's share of its wanted width falls to **47 %**
  (mobile `SessionScreen`) and **79 %** (a 520 pt desktop pane), against whole/99 % with the fix.

## T4 — `shortModelLabel` (RED → GREEN)

`app/lib/ui/composer/composer_selectors.dart`, `app/test/composer_selectors_test.dart`.

- RED: the helper does not exist. Pin these cases, because a silent `substring` bug blanks the
  pill: `anthropic/Claude Opus 4.6` → `Claude Opus 4.6`; `gpt-5.6-codex` → unchanged;
  `a/b/c` → `b/c` (first segment only); `/x` → `x`; `x/` → **`x/`** (the tail is empty, so fall
  back to the input rather than render nothing); `''` → `''`.
- GREEN: a pure top-level function. `ModelConfigPill` applies it to its label only.
- Same task: the pill's tooltip stops being the literal `'Model'`
  (`composer_selectors.dart:806`) and becomes the full `configValueName(model, value)`, so the
  provider stays recoverable on desktop. Test: rendered `Text` is short, `Tooltip.message` is long.
- **T4 owns acceptance criterion 3** (reviewer round 3): extend
  `composer_footer_space_test.dart` with footer-level assertions for the pi and codex shapes —
  unit tests of the helper alone would not prove the pill renders unellipsized in the real row.
  What landed, once measured: pi is whole at **393 pt** (`didExceedMaxLines == false`, width equal
  to its natural width) and **≥ 95 %** visible at 375 pt, where a 15-character name cannot fit at
  all; codex is whole at 375 pt, which required D5. The exact rendered strings are asserted
  (`Claude Opus 4.6`, `gpt-5.6-codex`), plus the full `provider/name` in the tooltip.

## T5 — call sites (RED → GREEN)

`app/test/session_screen_test.dart` (+ a desktop-pane equivalent), then
`app/lib/ui/session/session_screen.dart`, `app/lib/desktop/chat/desktop_chat_pane.dart`.

- RED first: pump the real `SessionScreen` for a pi-shaped session and assert the model label gets
  the width it wants. This fails while the ring is still in `footerActions`, even with T2 landed —
  which is the point. As landed: a 393 pt window (the screen's composer is 377 pt inside it), and
  the assertion is a **share** — ≥ 95 % of the label's wanted width — because at 377 pt a
  15-character name cannot be whole. Measured 47 % before, 99 % after.
- The fixture must be pinned or the test passes/fails for unrelated reasons (reviewer finding):
  1. seed `sessionUsageProvider` with non-null `contextTokens` **and** `contextWindow`, else the
     ring shrinks to zero and the starvation under test does not occur;
  2. seed a pi-shaped `configOptions` (`model` + `thought_level`) so a model pill exists at all;
  3. **focus the composer** — mobile leaves `alwaysExpanded` false, so the footer only renders when
     `alwaysExpanded || _isFocused` (`composer.dart:355`). The desktop pane sets it explicitly.
  Assert the ring and the model label are both present *before* asserting anything about ellipsis,
  so a fixture regression can never masquerade as a pass.
- GREEN: move `ContextUsageButton` into `footerTrailing` at both call sites. The SPEC-37 comment
  above it ("shown for every agent — it reads usage, not config") stays; it explains why the
  control exists, which is still true.
- Assert `worktree_starter.dart` is genuinely unaffected rather than assuming it: it passes no
  trailing control, so `flutter test` + `flutter analyze` staying green is the check.

## Risks

| Risk | Mitigation |
| --- | --- |
| A wide `footerTrailing` control from a future caller overflows the row | The parameter is documented as intrinsic-only and singular, and T3 asserts no exception at 320 pt with the 36 pt ring. A wider trailing control would fail that test — which is the intended signal, not a surprise. |
| `shortModelLabel` blanks a label for an unusual name | Degenerate cases pinned in T4; the function falls back to its input whenever the tail is empty. |
| Two models with the same name under different providers become indistinguishable in the pill | Accepted and reversible: tooltip (desktop) and picker sheet (both) show the full `provider/name`. Recorded in the spec (D2). |
| A golden churns on font changes | The golden covers the footer only; the behavioural assertions in T1/T3/T5 are the real guard. |
| T3 passes for the wrong reason after T4 shortens the label | T3 lands after T2 and runs GREEN with the **long**, unshortened label, asserting only criteria 1/4/5; its sensitivity is shown by the temporary miswiring check (ring back into `footerActions` → overflow reappears), not by a red run. The text-dependent criterion 3 lives in T4. |
| A fixture makes a test vacuously green (0 pt ring, unrendered footer) | T3 and T5 both assert the ring and the label exist before measuring them; the ring/footer preconditions are written into the plan rather than left to the implementer. |
