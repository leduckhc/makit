## Phase 1 · Contract first

### T1.1 — `RepoDTO` carries the forge and the effective worktree root

Both fields **optional**, so an older app paired with a newer server renders no row rather than a
fabricated one, and a newer app paired with an older server does the same (spec D5 forbids inventing a
value).

```ts
// server/src/protocol.ts
/** Which forge hosts this repo, as identified by forge/detect.ts. Absent when not yet probed. */
forge?: { software: ForgeSoftwareName; host: string; authed: boolean };
/** Effective worktree root for this repo (P1: the global value). Absent = unknown. */
worktreeRoot?: string;
```

- **RED TEST** — `server/test/fixtures/snapshots.json` gains a repo entry with both fields, and the
  existing snapshot guard test fails until `protocol.ts` admits them. Do **not** touch
  `server/test/fixtures/events.json`: it asserts one entry per *session* kind.
- **VERIFY** — `cd server && pnpm exec tsc -p . --noEmit && node --import tsx --test "test/**/*.test.ts"`
- **Committed alone**, before anything else, so no later task edits the contract.

### T1.2 — Populate `forge` in the repo snapshot

`repo_service.ts` builds `RepoDTO`. It needs the router to answer "what is this repo's forge", which
means the router must expose what it already learned during routing.

- Add `softwareFor(repoPath): ForgeSoftwareName | undefined` to the value returned by
  `createForgeRouter` (it already records per-repo decisions internally — this was drafted and removed
  once because the declared return type did not include it; declare it on the type this time).
- `authed` = whether a token was resolved for that host (`forgejoRefFromRemote(...).token !== undefined`),
  or, for GitHub, whether `gh` reported a usable budget. **Never** send the token.
- **RED TEST** — `server/src/repo_service.test.ts`: a repo whose router reports `forgejo` yields
  `dto.forge.software === 'forgejo'`; a repo the router has never routed yields `forge === undefined`
  (not a guessed value).
- **VERIFY** — as T1.1.

### T1.3 — Report the effective worktree root

- Extract `git.ts:33`'s expression into an exported `effectiveWorktreeRoot(env)` and have
  `repo_service.ts` put it on the DTO. **No behaviour change** — same value, now also reported.
- **RED TEST** — `server/src/git.test.ts`: `effectiveWorktreeRoot({MAKIT_WORKTREE_DIR:'/tmp/x'})` is
  `/tmp/x`; with an empty env it is `<home>/.worktrees`. Prove the bite by reverting the `??` default.
- **VERIFY** — as T1.1.

## Phase 2 · App vocabulary before app screens

### T2.1 — `RepoInfo.forge` + `RepoInfo.worktreeRoot`

- Mirror T1.1 in `app/lib/store/models.dart`, both nullable, decoded defensively (an unknown
  `software` string decodes to `unknown`, not a crash).
- **RED TEST** — `app/test/store/models_test.dart` (or the existing models test): a snapshot JSON
  without `forge` decodes to `null`; one with `software:"gitea"` decodes to `ForgeKind.gitea`; one with
  `software:"quux"` decodes to the unknown case.
- **VERIFY** — `cd app && flutter test --no-pub test/store/…`

### T2.2 — Monogram widget, shared with the home (spec D14, D15)

`RepoMonogram(name:, size:)` — deterministic hue from the name, first grapheme uppercased for a
multi-word name, lowercased single letter otherwise (match the mockup: `D`, `m`, `p`).

- **RED TEST** — same name yields the same colour across two builds; two different names in the
  mockup's set yield different colours; a name with a leading emoji or non-Latin first character does
  not throw and produces a non-empty glyph.
- **VERIFY** — `flutter test --no-pub test/ui/home/repo_monogram_test.dart`

### T2.3 — Delete the Dart-side forge guess (spec D15)

`forge_glyph.dart`'s `forgeKindForUrl` re-derives the forge from the PR URL. With T1.1 the server
answers it. Keep `forgeGlyphFor`/`forgeNameFor` (still needed for rendering), remove the URL rule and
its tests, and have `pr_detail.dart` read the repo's `forge` instead.

- **RED TEST** — a `pr_detail` widget test where the PR URL host and the repo's reported `forge`
  **disagree** (URL `codeberg.org`, forge `github`): the button must follow the *server*. This test
  fails today because the URL wins.
- **VERIFY** — `flutter test --no-pub test/ui/session/session_pr_test.dart test/ui/widgets/forge_glyph_test.dart`
- **Note** — this is a behaviour change to a shipped surface. If the reviewers judge it out of P1's
  scope, it moves to P2; it is listed here because leaving two sources of one fact is the drift D15
  exists to prevent.

## Phase 3 · The Settings section (the pixel target)

### T3.1 — `RepositorySettingsSection`

New `app/lib/desktop/settings/sections/repository_section.dart`, built from `SettingsSectionHeader` +
`SettingsGroup` + `SettingsResetButton`, rendering exactly the mockup's rows:

- `IDENTITY` — Logo (`from name`), Root path (+ copy), Git provider (`detected`), Default branch
  (`from remote`)
- `WORKTREES` — Worktree root (`inherited`)
- `LIFECYCLE SCRIPTS` — disabled group, `Not set`, `host only` tag

Group headers are **green uppercase** with a green uppercase page title above (matching the shipped
`SERVER & DEVICES` treatment). Rows are two-line: title + grey subtitle. Trailing reset slot present
and invisible on every P1 row (nothing is overridable yet) so alignment matches P2.

- **RED TEST** — widget test asserting: each group header present and in order; each row's label,
  subtitle and effective value; the badge text per row; that **no** row shows a reset button; that a
  repo with `forge == null` omits the provider row rather than rendering "unknown".
- **VERIFY** — `flutter test --no-pub test/desktop/settings/repository_section_test.dart`

### T3.2 — Sidebar group (spec D1, D2)

A `REPOSITORIES` group header after `About`, one entry per `pinned` repo with its monogram; selecting
one shows T3.1 with the repo name as the page title.

- **RED TEST** — the sidebar lists exactly the `pinned:true` repos, in the snapshot's order, and
  excludes `pinned:false` ones; the group header is absent when there are no pinned repos (no empty
  header).
- **VERIFY** — `flutter test --no-pub test/desktop/settings/…`

### T3.3 — Pixel audit against the mockup

Not a test — a **procedure**, per the `makit-mockup-vs-built-audit` and
`makit-capture-real-app-screenshots` skills:

1. Build and run the real macOS app; open Settings → the repo section.
2. Screenshot at a known width; place it beside the mockup card.
3. Compare row by row: header colour/case/tracking, row height, subtitle colour, badge shape and
   placement, trailing slot alignment, group corner radius, inter-group spacing.
4. Record each deviation and either fix it or justify it in the plan's Deviations log.

- **VERIFY** — the comparison images are read and every deviation is listed. A claim of "matches" with
  no image is not acceptable evidence.

## Phase 5 · QA (the part the user asked for by name)

### T5.1 — Integration test

Extend `app/integration_test/` (stub-backed, per `all_stub_test.dart` / `e2e_helpers.dart`) to open
Settings, select a repo section, and assert the identity rows against the stub's repo snapshot.

- **VERIFY** — the existing integration harness command (`app/tool/e2e-desktop.sh` for the desktop
  flow). One `flutter test` at a time — two concurrent runs collide over `.dart_tool` and the second
  dies with `Test directory "test" not found`, silently measuring nothing.

### T5.2 — Real app, driven

Open the built macOS app and drive it to the section using the computer-use skill
(`makit-computer-use` / `cua-driver`), capturing evidence. This catches what neither widget nor
integration tests can: real fonts, real window metrics, real theme, and the desktop-shell routing hazard
already recorded in the project skill (`desktop_sidebar.dart` calls `context.go` under a shell with no
GoRouter — it throws at runtime while tests pass).

- **VERIFY** — screenshots of the real app at the section, read and reported.
