## Core logic

### `server/src/pairing/cert.ts` — `tailscaleIP()` rewrite

The detection function is rewritten end-to-end. The old version parsed `tailscale status --json` via a shell-spawning `execSync` with a bare binary name. The new version probes four candidate paths, uses `execFileSync` (no shell), and forces the macOS app-bundle executable into CLI mode.

```ts
export const TAILSCALE_BINARIES: readonly string[] = [
  "tailscale",
  "/usr/local/bin/tailscale",
  "/opt/homebrew/bin/tailscale",
  "/Applications/Tailscale.app/Contents/MacOS/Tailscale",
];

export type TailscaleRunner = (bin: string, args: string[]) => string;

const defaultTailscaleRunner: TailscaleRunner = (bin, args) =>
  execFileSync(bin, args, {
    encoding: "utf8",
    timeout: 2000,
    stdio: ["ignore", "pipe", "ignore"],
    env: { ...process.env, TAILSCALE_BE_CLI: "1" },
  });

export function tailscaleIP(run: TailscaleRunner = defaultTailscaleRunner): string | null {
  for (const bin of TAILSCALE_BINARIES) {
    try {
      const out = run(bin, ["ip", "-4"]);
      const ip = out
        .split(/\r?\n/)
        .map((line) => line.trim())
        .find((line) => line.startsWith("100."));
      if (ip) return ip;
    } catch {
      // Not found at this path (ENOENT) or the command failed — try the next.
    }
  }
  return null;
}
```

**Pseudocode** (the diff is dense enough to warrant it):

```
for bin in [bare, /usr/local/bin, /opt/homebrew/bin, Tailscale.app/MacOS/Tailscale]:
    try:
        out = exec(bin, ["ip", "-4"], env += TAILSCALE_BE_CLI=1)
        for line in out.splitlines():
            if line starts with "100.": return line
    catch: continue
return null
```

**Callouts**

- **`Subtle` — `execFileSync` replaces `execSync`.** No shell is involved, so the hardcoded paths in `TAILSCALE_BINARIES` can't be shell-interpolated. This is a quiet security improvement; if you scan the diff for "what changed" you might miss it because the call shape is similar.
- **`Subtle` — `TAILSCALE_BE_CLI=1` is set on every candidate, not just the app-bundle path.** The comment says "harmless for standalone/Homebrew binaries." That's an assumption about third-party CLIs. Probably fine, but if a future Tailscale CLI starts gating behavior on that env var, every binary in the probe list is affected — not just the macOS app executable.
- **`Subtle` — per-path `try/catch` swallows everything, not just `ENOENT`.** A binary that exists but exits non-zero (e.g. `tailscale` not logged in, returns exit 1) is treated identically to a missing binary and falls through to the next candidate. Correct for this function's purpose, but means a misconfigured-but-installed Tailscale on the first path will silently retry against `/Applications/...` and may return a different machine's IP if both binaries exist. The probe order matters.
- **Testability — `TailscaleRunner` is injectable.** `tailscaleIP(run = defaultTailscaleRunner)` lets `cert.test.ts` exercise the PATH-fallback and CLI-mode logic without a real `tailscale` on the machine. The last test (`forces the macOS app executable into CLI mode`) writes a shell script that exits 1 unless `TAILSCALE_BE_CLI=1` and runs the real `defaultTailscaleRunner` against it — that's the test that proves the env var actually reaches the child, not just that it's in the source.

### `app/lib/store/store.dart` — `refreshRepos()` becomes best-effort

```dart
Future<void> refreshRepos() async {
  try {
    await _ref.read(connectionControllerProvider.notifier).request(
      MsgType.cmd,
      {'kind': 'repo.refresh'},
    );
  } catch (_) {
    // Swallow: the repo snapshot is refreshed by the server on its own for
    // the operations that call this.
  }
}
```

And at the two call sites in `addProject` / `removeProject`:

```diff
-    await refreshRepos();
+    unawaited(refreshRepos());
```

**Callouts**

- **`Subtle` — `catch (_)` swallows *all* errors, not just `unknown cmd`.** Intentional: a transient network error during pull-to-refresh shouldn't surface to the user either. The trade-off is that a programming error in the request path (bad serialization, null `_ref`) is now invisible here with no log line. If `repo.refresh` ever starts failing silently in production, this catch is the first place to look.
- **`Subtle` — `unawaited()` and `try/catch` are independent safety nets and both are required.** `unawaited` fixes the latency bug (mutation no longer blocks on the refresh reply). `try/catch` fixes the error-propagation bug (a pre-SPEC-11 server's `err` no longer surfaces). Removing either one regresses a real fix; the tests cover both independently — "mutations do not wait for a dropped repo.refresh" pins the `unawaited` (via `.timeout(100ms)`), "addProject succeeds when server rejects repo.refresh" pins the `catch`.
- **`Perf` (positive) — pull-to-refresh still awaits.** `refreshRepos()` returns `Future<void>`; the pull-to-refresh gesture can still `await` it for the spinner. Only the mutation paths use `unawaited`. The function signature didn't change, which is what makes the call-site-only change safe.

## Wiring & integration

### `app/lib/pairing/pairing_screen.dart` — one-line addition to the fake-data button

The `useFakeServer()` call in the "Open with fake data" `onPressed` gets a follow-up:

```dart
ref.read(connectionControllerProvider.notifier).useFakeServer();
ref.read(onboardingControllerProvider.notifier).skipNotifications();
context.go('/');
```

**Why this is the crux of fix #2, despite being one line.** The fake-data shortcut is a dev path that bypasses pairing entirely, but the router doesn't know it's a dev path — it routes strictly on `onboardingStep`. Without clearing the notifications gate, `paired=true` is unreachable from the router's perspective. The fix is in the right place (the shortcut clears the gate it's bypassing) rather than the wrong place (loosening the router's ready check).

**Concrete trace — the surprising behavior change.** A reviewer reading just the diff might not see why Home "bounces back" rather than failing to navigate at all. The state-transition order is the load-bearing detail:

```
Fresh install, OS notification permission = notDetermined.

BEFORE:
  tap "Open with fake data"
  → useFakeServer(): paired = true
  → context.go('/')
  → router redirect: onboardingStep != ready (still on notifications step)
  → redirect back to onboarding
  → screen flashes Home for one frame, vanishes            ← the bug

AFTER:
  tap "Open with fake data"
  → useFakeServer(): paired = true
  → skipNotifications(): notifications gate cleared
  → onboardingStep transitions to ready
  → context.go('/')
  → router redirect: onboardingStep == ready → stay on Home
  → 1s later: still on Home                                ← test asserts this
```

The divergence step is the order of `paired=true` vs the gate check. The fix inserts the gate-clearing between them.

## Reviewer notes (cross-file)

- The `tailscaleIP` rewrite and the `refreshRepos` rewrite are *the same shape of fix*: a side-channel call (Tailscale detection / `repo.refresh` reply) was allowed to fail the primary action (binding the QR host / acknowledging the project mutation). Both fixes convert the side channel to best-effort. Reading them as a pair makes the PR's thesis legible.
- The fake-data fix is the only one that touches router-reachable state (`onboardingStep`). The other two are confined to transport and host-detection. That's why the fake-data fix is the only one that needed a widget test through the real GoRouter — the other two are unit-testable because they don't cross the router boundary.
- `_SnapshotTransport.dropRepoRefresh` is a small test-infrastructure addition that materially improves what the test suite can express. A dropped reply is a different failure mode than an error reply, and being able to assert "the mutation completed in <100ms anyway" is the only way to unit-test `unawaited` semantics. Worth keeping in mind when writing future transport tests.
