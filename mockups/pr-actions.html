PR actions & pills — baseline vs three directions

The bar above the desktop composer (app/lib/desktop/chat/pr_bar.dart), its pills (pr_state_style.dart), the canned actions (pr_actions.dart) and the mobile sheet (then pr_sheet.dart, since replaced by pr_detail.dart). Tokens, type and geometry are the real ones — dark-mode primary #4ADE80, the 28px control height that ships, Phosphor Light icons.

Outcome — direction B was chosen and built (flavour B1).
This page is the survey that led to that call; it is kept as the record of what was compared, so A and C here were never built. The as-built reference is mockups/pr-actions-next-step.html, which also lists where the mock diverged from the implementation.

What survived from this page into the shipped design, regardless of direction: the lifecycle-driven CTA (a specific verb only when there is a specific next step, otherwise it rests), the two action registers (tonal “ask the agent” vs filled “do now”), the regrouped menu with inapplicable prompts greyed and explained, the precedence table in §4, and the two endings a PR can have — Wrap up and Discard worktree. Plus Mark ready and Update branch, which were flagged here as speculative and later asked for.

4 · Behaviour: two kinds of action

Today every action is "insert a prompt for the agent" — even deterministic git/gh operations. That's why the buttons feel general-purpose. Split them, and mark them differently: tonal = ask the agent (inserts a prompt into the composer, never sends — as today), filled = do it now (a server command, with a confirm when destructive).

The table is also the precedence order. The CTA is the first row that matches, top down — so uncommitted work outranks a red build (you cannot fix CI without committing), and a merged/closed PR outranks everything (its checks and threads are history). The first four rows keep the exact precedence _situationFor() already ships; the new states slot in around them.
Menu, regrouped. The caret no longer dumps all six prompts regardless of state. It groups by kind, puts the relevant ones first, and keeps the irrelevant ones visible but disabled with the reason — the same "explain the block, don't hide it" convention worktree_actions.dart already uses for a disabled Rename.
