The expanded tool body

The collapsed row is done (see mockups/tool-one-liner.html). Unfolding one still lands you in the old design: a black monospace heading over a box inside a box, repeated per section. This board diagnoses why it reads as clutter and offers two ways out, plus the one rule that fixes most of it.

Every grey is a real theme.dart token; the light strip in §2 is the same theme the pasted screenshot was taken in. Code-block colours are the actual atom-one-dark / github highlight themes the app loads.

1Six causes, not one bad taste

All six live in two widgets, so all six are fixable in one pass.

  1. The section title is a heading, in a code face. titleSmall.mono = 14 px w600 at full onSurface — heavier and larger than the content it labels, and monospace for a word that is not code. Two of them stack up per body. tool_renderers.dart:158 — Text(title, style: titleSmall?.mono)
  2. A box inside a box. ToolSection wraps its child in a surfaceContainer panel at radius 10 with 12 px padding; ToolCodeBlock is itself a panel — different fill, its own hairline, radius 8, another 12 px padding. Two frames and 24 px of inset around one line of output. tool_renderers.dart:160-172 + 205-215
  3. A short result is rendered as source code. 307 lines goes through ToolCodeBlock, so a highlighter tints the digits teal and a copy button rides on top of it. It is a fact, not a payload. _ReadRenderer.body → ToolSection('Content', ToolCodeBlock(...))
  4. The key/value column is 72 px wide, always. path ends up marooned four characters into a 72 px gutter, and its value wraps at whatever width is left — three ragged lines for one path. tool_renderers.dart:263 — SizedBox(width: 72, …)
  5. The body re-states what the header just threw away. Expanding replaces Read app/lib/…/tool_call_card.dart with Read, so the very first thing the body must do is print the path again — as a titled box. tool_call_card.dart:_line() — expanded ? toolLabel(item) : toolSummaryLine(item)
  6. The path is not compacted here. The collapsed row shows it relative to the worktree; the body prints /Users/le/.worktrees/makit/feat-chat-content/app/lib/… in full, which is what forces the wrap in D4. compactPathsIn() is applied to the summary line only
Measured, from the running app. An expanded bash row's accessibility frame is 249 px tall for a one-line command and a one-line output. The chrome — two headings, two outer panels, two sets of padding, the 16 px inter-section gap — is about 120 px of that. The content is ~34.

3A — the header keeps the subject; the body is just the payload

One idea does most of the work: stop emptying the header on expand. If the row still reads Read app/lib/ui/session/tool_call_card.dart while open, the body never needs an “Arguments” box — and what is left is one payload, which already knows how to draw itself. Captions appear only when a body has two payloads; short facts become a dim strip, never a panel.

Why not: it is the shortest body on the board and the worst. A transcript is a document you scan and copy out of; hiding the command behind a tab means the thing you most often want to re-read costs a click, and it adds a second interactive control to a row whose whole point is one tap = one disclosure.

5The five rules behind A

ruleas builtproposed
The subject stays put Expanding swaps the one-liner for the bare verb, so the body opens with an Arguments box repeating it. The header keeps its full line while open. Single-argument tools (read/write/edit/grep) lose their arguments section entirely.
One frame per payload ToolSection panel (radius 10, pad 12) wrapping a ToolCodeBlock panel (radius 8, pad 12, hairline). The payload block is the only box. Sections contribute a caption and nothing else.
Facts are text, payloads are blocks Everything is a box: 307 lines gets a highlighter and a copy button. No newline and <80 chars → a dim key value in the facts strip. Exit code, match count and line count live there too.
The payload sits in the app's ramp #282C34 (dark) / #F0F1F4 (light) — atom-one-dark's and github's own panel colours, a blue-grey that belongs to neither theme's neutral ramp. Part of why the body reads as foreign to the transcript around it. surfaceContainerLowest (#121212 / #FFFFFF) with a hairline. Token colours keep highlighting the code; the panel stops being a guest.
A caption, not a heading titleSmall.mono — 14 px w600 mono at full onSurface. labelSmall 10 px uppercase, onSurfaceVariant, letter-spacing 0.07em — and only when a body has two or more payloads.
What this is worth. The bash body measured 249 px for one line of command and one line of output; variant A draws the same information in about 132, and a read goes from ~250 to ~118 — while showing more content, because the space freed is given back to the payload (which is still capped at kToolExpandedMaxHeight = 340 and scrolls).
✓ Shipped — and five things found by running it. Verified on macOS (dark, 430 pt) and the iPhone 17 simulator with flutter run -t tool/tool_row_demo.dart --dart-define=unfold=true.
  • Rule 5 needed a second fix that a passing test hid. Colouring ToolCodeBlock's container was not enough: HighlightView paints theme['root'].backgroundColor inside it, so the real app still rendered atom-one-dark's #282C34 while a widget test asserting the container's colour was green. The highlight theme's own panel is now stripped (_withoutPanel), and the test asserts the theme map, not just the box. Measured after: #131313 — the app's ramp.
  • A maximum-length fact overflowed by 147 px. isFactResult allows 80 characters, which is wider than a 430 pt pane, and the Wrap → Row could not shrink. Values are Flexible now, pinned by a sweep that renders a max-length fact through the whole row at 320 / 430 / 560 / 760 pt — the class of bug, not the one instance.
  • A diff payload lost its frame. DiffText and DiffLineRow never drew one — they borrowed it from the old ToolSection container, so once that went away an edit body rendered as full-bleed tinted bands beside neatly panelled neighbours. The frame now lives in one ToolPanel applied by ToolBlock, so “one frame per payload” holds by construction for code and diffs alike, and ToolCodeBlock draws only code.
  • The panel-count test was measuring nothing. It counted every coloured DecoratedBox — and a diff row is a coloured box, so the assertion was vacuous exactly where it mattered. It now counts ToolPanel widgets. Second time on this board that a green test hid a visual defect; both times the test asserted a mechanism instead of the outcome.
  • The “one-line result” card contradicted rule 1. It drew a command caption over a single payload. Shipped behaviour is the uniform rule: a caption only when two or more payloads render, so a shell row whose output is a fact shows the command block bare — shell text needs no label saying it is a command.

Asked before building — and answered. Variant A deletes the “Arguments” section for single-argument tools by keeping the path in the header, which also means the expanded header no longer shrinks to the bare verb. That was a visible change to a row already signed off, so it was put to the author, who chose A without a path fact: the path would only duplicate the line directly above it. The fallback (A plus a path fact, one line taller, as drawn in the B card) was not taken.
