Performance dashboard — footer pill + full panel

The efficiency claim, made checkable. Hover the footer mark → one-line read. Click → the popover: three sparklines (app / server / agents), a per-agent row list, and the makit total. “Open dashboard” → the full panel with stacked CPU, memory, frame times, event-loop lag, wire throughput, a process table and a snapshot export. Colours are sanctioned tokens from app/lib/app/theme.dart: violet = app, amber = server, green = agents.

Hover anything to read its explainer. Press G to outline every element that has one.

6 · Why the naive version lies

these three decide whether the dashboard is evidence or decoration
  1. ps -o %cpu is a lifetime average, not current CPU. An agent that pinned a core for 3 s and then idled for ten minutes reports ~0.5% forever. We must sample cumulative CPU time and compute Δcpu ÷ Δwall between ticks. Get this wrong and every number on the panel is a lie in your favour — which is worse than no panel.
  2. An agent is a process tree. pi and codex spawn bash, ripgrep and node. Charging only the direct child under-reports by multiples (1.22 GB → ~180 MB in the example above). Fix: one ps -axo pid,ppid,rss,time per tick, build the ppid tree once, sum descendants per agent root. One exec covers every agent — never one exec per pid.
  3. The meter must not distort the measurement. Sample at 1 Hz only while a subscriber is watching, keep a coarse 5 s ring otherwise, and never persist samples to the SQLite event log — it is append-only. The panel shows its own cost so the reader can check that claim rather than take it.

One more, smaller: the app has no self-CPU API in Dart. Memory is ProcessInfo.currentRss, but for CPU the app sends its own pid in hello; when the app's host matches the server's host — the normal desktop case — the server samples it with the same collector as everything else. One code path, no platform channel. When they differ (phone on the tailnet), the app row shows memory only and says so, rather than inventing a number.

7 · Explainer copy, for review

every tooltip in one place — easier to edit as prose than by hovering
ElementTooltip
TitleLive resource cost of everything makit runs on this machine: the Flutter app, the Node server, and every agent process tree they spawned. Nothing off-machine is counted.
“1 Hz · live”Sampling only runs while this panel is open (1 Hz). When it closes, makit falls back to one coarse sample every 5 s, kept purely in memory.
Total headlineSum of resident memory across app + server + all agent trees. Resident, not virtual — the number the OS actually holds in RAM for you.
“idle” captionIdle means no turn is in flight. This is the state makit is in for most of its life, so it is the number the efficiency claim actually rests on.
App rowThe Flutter desktop UI process. Memory comes from ProcessInfo.currentRss; its CPU is sampled by the server, which lives on the same machine — one collector, no platform channel.
Server rowThe Node server: WSS transport, session manager, SQLite event log. Its own process.memoryUsage().rss and CPU from process.cpuUsage() deltas — exact, no ps needed for self.
Agents rowAll agent process trees summed. A parked agent still holds its runtime resident — that resident cost is the honest price of instant resume.
Agent sparklineGreen spikes are turns. Between them the line should sit on zero — “0.0% while parked” is the headline number.
Parked agent rowProcess alive, no turn in flight, 0.0% CPU. Resume is instant because we did not kill it.
Working agent row1.22 GB is the whole tree: the codex process plus the ripgrep/bash/node children it spawned for this turn. Attributing only the direct child would have reported ~180 MB — wrong by 7×.
Comparison bannerThe comparison that makes the number mean something. Baselines are measured once on this machine by makit bench, not hardcoded — an unverified boast is worse than no boast.
CPU % axisPercent of one core. On a 12-core machine the ceiling is 1200%, so 96% means “one core busy”, not “machine saturated”. The dashed line marks 100% = one full core.
Turn shadingShaded columns are turns, drawn from the same turn-start/turn-end events the transcript uses — so cost lines up exactly with what you asked for.
Memory chartAgent memory steps up during a turn and does not fully return — runtimes keep their heap. That plateau is the honest cost of a parked session. A real leak looks like a staircase that never comes down across several turns.
Frame p9595% of frames finished building and rasterising faster than this. Under 16.7 ms means the UI held 60 fps even while the agent burned a core.
Dropped framesFrames that missed the 16.7 ms budget. Above ~0.5% you can see it as a stutter while scrolling a long transcript.
Event-loop p9999th-percentile Node event-loop delay. Under 10 ms is healthy; over 100 ms and every connected device feels the lag. Spikes almost always mean a synchronous SQLite or JSON call on a hot path.
Wire KB/sWebSocket bytes per second, both directions. Streaming one turn should cost single-digit KB/s — if it does not, we are re-sending state we should have diffed.
Event log MBSize of the SQLite event log in ~/.makit/. It is append-only, which is why performance samples are never written to it.
CPU columnCurrent CPU, computed as Δcpu-time ÷ Δwall-time between two samples. Not ps %cpu, which is a lifetime average and would report ~0.5% for a process that pinned a core three seconds ago.
CPU-s columnTotal CPU seconds since the process started. The honest cumulative bill — the one number that cannot be gamed by choosing a flattering sampling window.
PID columnOperating-system process id, for cross-checking against Activity Monitor or htop. If our number disagrees with theirs, ours is wrong.
Range selectorWindow over the in-memory ring buffer. 30 min is the whole ring; beyond that nothing is retained — samples are deliberately never written to the append-only event log.
FreezeFreeze the charts so you can read a spike without it scrolling away. Sampling continues underneath.
Set baselineMark the current numbers as a baseline. A later snapshot is diffed against it, so you can prove an optimisation worked instead of trusting a memory of yesterday's chart.
Export snapshotWrite the whole window — every sample, every process, plus machine and version info — to JSON and a pasteable markdown summary. This export is the shareable artifact behind the efficiency claim.
Self-cost rowWhat this panel itself costs while open: sampling, charting and pushing frames. Shown because a meter that distorts its own measurement is not evidence. Closing it returns the cost to zero.

Tooltips explain rather than restate — “CPU: the CPU usage” is noise. Each answers why does this number matter or what would I do about it. Same Tooltip widget as the rest of the app, ~600 ms delay, wrapped max-width, since these are sentences.

8 · Interaction & data summary

Hover icon → one-line tooltip, ~500 ms delay.
Click icon → popover opens collapsed and starts 1 Hz sampling; click-outside / Esc dismisses and stops it.
History pill → expands detail in place, animating height (~160 ms); state persists across opens and restarts.
Open dashboard → an in-window overlay, the same mechanism Settings uses (settingsOpenProvider + DesktopWindowBody), so the chat underneath stays alive. Not a workspace tab: Tab carries only a sessionId, and a kind tag would ripple through persistence, drag/drop, group membership and pruning. Unlike Settings, the chat is left interactive — you must be able to drive a session while watching what it costs.
Agent row → click reveals the tool children; the row menu offers “park” and “end session”.
Idle behaviour → with nobody watching, one coarse sample every 5 s into a 30-minute in-memory ring, so the charts have history the moment you open them. Disableable in settings, in which case the icon shows the Off state.
Wire → a new top-level metrics.sample frame gated behind sub { metrics: true } — not a session event kind, since metrics are host-wide and must stay out of the append-only log.
Persistence → none, by design. Ring buffers only; the sole way a sample leaves memory is Export snapshot, at your request.
