Mid-turn messages — steer vs queue

SPEC-35 UX candidates. The problem: you type while the agent is working, and what happens next is decided by the transport, not by you. On codex the message is steered into the running turn (immediate, irreversible). On an ACP agent it is queued until idle (cancellable). Same keystroke, two consequences.

Shipped today: one send button, always enabled while running · queued messages appear as cancellable chips above the composer · a steered message is captioned Steered into the running turn on its bubble. Everything below is a proposal on top of that.

Each card is interactive — type and press the button. The agent switch flips the pane between a steering transport (codex) and a queue-only transport (pi/ACP), because the point of most of these designs is that the user should not have to know which they are on.

A · Intent-ahead composer recommended no new gesture

The cheapest fix for the real complaint. While the agent is working, the composer says what pressing send will do: the placeholder and the send glyph change, and a one-line hint sits under the field. Amber arrow-into-stream = will steer. Grey stack = will queue.

No extra buttons, no modes, no protocol flag beyond a steering capability on the session.

agent
state: running

Why

  • Sets expectation before the irreversible action, not after.
  • Zero added pixels, zero new gestures, works identically on phone and desktop.
  • Teaches the concept passively — after two sessions you just know.

Risks

  • Another moving part in the composer; must not animate on every token.
  • Amber send button may read as "warning" — needs a real colour pass.
Cost: app-only except one bit: the app must know whether steering is possible → steering on SessionDTO (derived from the adapter, ~15 lines server). Composer: placeholder + glyph + hint driven by session.status.

B · Grace window — "pull it back" recommended fixes the real bug

The known complaint about codex steering is that an accidental steer cannot be undone. makit can fix that without any protocol support: hold the message on the server for ~3 s before calling turn/steer. During the countdown it is an ordinary pending chip with a draining ring — one tap pulls it back into the composer, text intact.

After the ring empties it steers for real and becomes a captioned bubble.

grace: 3 s · configurable, 0 = off

Why

  • Turns an irreversible action into a reversible one — the steering complaint.
  • Reuses the queue machinery already shipped: it is a queue entry with a timer.
  • Same affordance for both transports, so the asymmetry shrinks by itself.

Risks

  • Delays a deliberate steer by 3 s — the agent may pass the step you aimed at.
  • Needs a "send immediately" escape (double-press, or tap the ring).
Cost: server-side timer in session.ts around the existing steer() call + a graceMs on the queue entry so the chip can render the ring. No new wire concepts — a pending message already exists.

C · Queue tray — reorder, edit, promote only if queues grow

Today's chips are a flat list you can only cancel. If real use produces 2–4 pending messages, the strip should become a small tray: drag to reorder, tap to edit before it flushes, and ⤒ promote = stop the current turn and send this one now (interrupt, the third behaviour we already have but never surface per-message).

pending: 3
waiting for the agent

Why

  • Editing a queued message is strictly better than cancel + retype on a phone.
  • Per-message promote exposes interrupt where it is actually wanted.
  • Speculative: nobody has yet queued three messages in makit.

Risks

  • Drag inside a scrollable composer area is fiddly on mobile.
  • Edit needs an id-stable update cmd (queue.update) — new surface.
Cost: medium. Two new cmds (queue.update, queue.promote), reorder semantics on the server queue, and a real drag implementation. Do not build until the one-chip case has been used in anger.

D · Steer seam in the transcript reading back

The shipped caption tells you that a message was steered. A seam tells you where it landed: a hairline across the agent's output at the point the steer was injected, so a long turn reads as "…this part, then I redirected it, then this part". Answers "why did it change course?" three days later.

Why

  • Explains a mid-turn change of direction when re-reading a long session.
  • Pure render of data we already have (the echo's position in the log).

Risks

  • Another horizontal rule in a transcript that already has tool rows.
  • The seam is only truthful if the echo is ordered where the steer landed — it is (we emit on acceptance), but streaming deltas can arrive around it.
Cost: app-only, small. A steered UserMessageItem already sits between the agent's chunks; this is one extra row widget in chat_transcript.dart.

E · Ghost bubble at the tail alternative to chips

Instead of a chip above the composer, a queued message renders where it will land: a dashed, dimmed bubble at the end of the transcript, captioned "sends when the agent finishes · cancel". Spatially honest — the queue is the future of the conversation.

Why

  • Zero new chrome; uses the space the message will occupy anyway.
  • The transition "ghost → real bubble" on flush is self-explanatory.

Risks

  • Touches the transcript. A synthetic tail row interacts with SPEC-21 anchoring, SPEC-34's index-keyed markers, and the trailer row (ask card / spinner).
  • Scrolled up, you cannot see your own pending message at all — the chip is always in view, this is not.
Cost: app-only but risky: a fake item in the folded list, or a second trailer. That is exactly the class of change SPEC-21/34 warn about. Chips stay cheaper and safer.

F · Explicit choice: split send / long-press rejected in SPEC-35

For comparison: the option you asked about. Send stays primary; a caret opens Queue instead and Stop & send now. Shown here so the cost is concrete rather than hypothetical — on a queue-only agent the menu collapses to nothing, which is the tell that it needs capability plumbing to avoid lying.

two real choices

Why not (yet)

  • Needs send.message.mode and a steering capability on the DTO, or the second item is a no-op on pi.
  • Two gestures to learn for a distinction most users will never care about.
  • …but it is the only design that lets you deliberately hold back on codex.
Cost: highest of the six. Wire flag + capability + menu on two surfaces + shortcut. Revisit if "let it finish first" turns out to be a frequent want.

What I'd actually build

  1. A (intent-ahead composer) first. It attacks the actual defect — the user cannot predict an irreversible action — and it costs one capability bit plus composer polish. Everything else is cosmetics until this exists.
  2. B (grace window) next, defaulting to ~2.5–3 s on steering transports. It converts the one genuinely bad property of steering into a recoverable one, reuses the queue we already have, and makes both transports feel the same for the first three seconds.
  3. D (seam) when a long steered session first confuses you. Cheap, additive, read-time value.
  4. C and E: don't. C is speculative until queues routinely exceed one message; E buys spatial elegance by touching the one part of the app (reversed anchored transcript) that SPEC-21/34 tell us to leave alone.

F stays rejected until someone says "I wanted it to finish first" out loud. The shipped caption is retained in every option — it is the only thing that makes the behaviour learnable.
